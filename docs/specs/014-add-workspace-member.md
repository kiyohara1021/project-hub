# 登録済みユーザーの所属追加

## 目的・範囲

基本画面/API案に残る所属追加を実装する。管理者が事前登録済みのテストユーザーIDを指定し、同じworkspaceの全プロジェクトを閲覧できる所属を付与する。プロフィールの検索範囲は拡大しない。

## 受け入れ条件

- adminだけ「メンバーを追加」から登録済みUUID・ロールを指定できる。初期ロールはviewer。追加前にID・ロール・全プロジェクトへの閲覧権限を確認する。
- POST `/api/v1/workspaces/:wid/members`、JSON `{user_id,role}`、Idempotency-Key必須（1〜128字の英数字/_/-）。未知/欠落キー、無効UUID・roleは400。JWT、Origin、JSON32KiBを既存更新APIと同様に検証する。
- 新規追加201 `{data:{user_id,role,version,joined_at}}`。対象profile不存在404、既存所属409 `ALREADY_MEMBER`。重複で既存ロールを書き換えない。member/viewerは403、無所属404、未認証401。
- DBのworkspace行ロック後にauth.uid()のadmin権限を再確認。所属・監査・再送記録は単一トランザクション。直接INSERT、anon/member/viewer/他workspaceからのRPC追加は拒否する。
- 同一workspace/actor/path/keyの同一本文は24時間同じ成功応答を再送し、監査・所属を重複させない。異なる本文は409。再送でも現在の管理権限を確認する。過去成功後に所属が変更・解除されていても再送は当時の受付結果のみを返し、復元やロール上書きをしない。再追加は新しいキーを使う。
- 送信中の二重操作を防ぎ、通信失敗時は同じ内容・キーで再試行可能。エラー時入力保持、項目不正時フォーカス、確認画面からの見直し、Esc・終了時フォーカス復帰、360pxを確認する。
- 追加本人は所属workspaceを閲覧可能。既存ロール変更・所属解除・最後のadmin保護を維持する。プロフィールの全ユーザー検索、メール、一般登録、ユーザー作成は対象外。

## DB・認可

`add_member_once`はSECURITY DEFINER、固定search_path、既存専用所有者、authenticatedだけにEXECUTEを付与する。再送用privateテーブルはRLS有効・API非公開、通常ユーザーの直接アクセス不可。既存テーブル構造・ERの業務関係は不変。既存監査INSERTトリガーを利用する。

## 検証

DBテストで権限・プロフィール非公開維持・同時追加・再送/本文違い・24時間期限・ロール変更/解除後の再送・再追加・原子的監査を確認。認証E2EでAPI契約、管理者限定UI、確認・入力保持・成功更新・360pxとキーボード操作を確認する。
