# プロジェクトの公開範囲と参加者

Issue: [#78](https://github.com/kiyohara1021/project-hub/issues/78)。実装中。既存のワークスペース分離に、プロジェクトごとの閲覧範囲を追加する。

## 目的・権限

- 公開範囲は`workspace`（ワークスペース全員）と`private`（管理者と指定した参加者）。既存プロジェクトは`workspace`のままとする。
- どちらの範囲もワークスペースへの所属が必須。ワークスペース管理者は全プロジェクトを閲覧・管理できる。
- 参加者に追加してもワークスペースのロールは変えない。viewerは閲覧のみ、memberはタスク・課題・コメントを変更できる。アーカイブは従来どおり閲覧のみ。
- 作成・公開範囲変更・参加者の追加/解除は管理者のみ。新規作成時から非公開を指定でき、公開状態を経由しない。
- 参加者一覧は管理者が管理画面で取得する。ユーザーIDを指定できるのは同じワークスペースの所属者だけ。直接のテーブル書込は許可しない。
- 範囲・参加者の変更はプロジェクトのversionで競合を検出する。workspace→projectのロック順を保つ。

## 閲覧の境界

非参加者にはプロジェクトの存在を示さない。一覧・詳細・カンバン・課題・コメント・ガント・操作履歴・ダッシュボード集計・担当件数・最新5件をDBのRLSで絞る。ID直指定の読取と更新は存在しないIDと同じ404とする。所属一覧とプロフィールはワークスペースの共通情報のため従来の閲覧範囲を維持する。

読取集計RPCはSECURITY INVOKERを維持する。更新RPCは所有者権限で動くため、`assert_task_writer`内でも現在の閲覧権限を検査し、再送記録を返す前に検査する。公開範囲の検査は`auth.uid()`から操作者を決める。

## 担当者と失効

非公開のタスク・課題には、そのプロジェクトを閲覧できる所属者だけを割り当てる。画面の候補も同じ範囲とする。DBトリガーでも検査する。公開範囲を非公開に変更した場合、参加解除した場合、管理者から降格した場合に閲覧できなくなる担当者は未割当にする。対象タスク・課題のversionと履歴を更新する。所属解除はプロジェクト参加も解除し、再所属だけでは復活しない。

## 操作履歴の保持

操作履歴は削除しない。現在の公開範囲と参加者で閲覧を判定するため、非公開化すると過去のプロジェクト履歴も非参加者から見えなくなる。公開に戻すと過去の履歴もワークスペース全員が閲覧できる。

通常はプロジェクトをアーカイブし、削除APIは追加しない。管理用のDB操作でプロジェクトを削除した場合も、削除時点の公開範囲・参加者をprivate領域へ保存して履歴だけを保持する。既に削除済みの旧プロジェクトの履歴は、旧仕様どおりworkspace範囲とする。所属解除時は削除済みプロジェクトの参加情報も消し、再所属による権限復活を防ぐ。管理用の保存情報を一般ユーザーに直接公開しない。

## API・UI

- 作成APIは任意の`visibility`を受け付ける。省略時は`workspace`。旧入力と24時間以内の既存再送記録に互換性を保つ。
- `GET /api/v1/workspaces/:wid/projects/:pid/access`は管理者向けに公開範囲・version・参加者IDと候補一覧を返す。
- 同URLの`PATCH`は`visibility`、`member_ids`（重複不可・最大100人）、`version`を受け付け、参加者一覧を原子的に置き換える。
- プロジェクト一覧に公開範囲を表示し、管理者には「公開範囲」ダイアログを用意する。作成画面で非公開を指定できる。

## 受け入れ条件

- DBでworkspace/public/private、admin/member/viewer/outside、他のワークスペース、未認証の組み合わせを検証する。
- 一覧だけでなく直接SELECT・すべての更新RPC・再送・ダッシュボード・担当件数・操作履歴・コメントに非公開の情報が混入しない。
- version競合、対象外ユーザーの参加追加・担当割当拒否、非公開化/参加解除/管理者降格/所属解除時の担当解除と履歴を確認する。
- 既存の公開プロジェクト、所属解除、最後の管理者、削除後の履歴保持を回帰確認する。
- APIのOrigin・入力・権限・404同一応答を確認し、PC/360pxで作成・公開範囲編集・競合復旧・キーボード操作を確認する。
