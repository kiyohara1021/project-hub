# 一般ユーザー登録と利用開始

Issue: [#75](https://github.com/kiyohara1021/project-hub/issues/75)

## 目的・範囲

メールアドレスの所有を確認して利用を開始し、自分のワークスペースを作成できるようにする。登録、確認メール、パスワード再設定、初回ワークスペース作成を扱う。課金・顧客管理、SNS認証、多要素認証は対象外。

## 契約

- 接続モードかつ`SELF_SERVICE_AUTH_ENABLED=true`の環境で登録・再設定を提供する。Previewでは送信しない。本番はSMTP・確認テンプレート・Supabase登録許可を確認後に有効化する。
- 登録はメール、12〜128文字のパスワード、1〜80文字の表示名。確認前にはセッションや所属を与えない。登録済みメールかどうかは成功案内で区別しない。
- 確認リンクのGETではトークンを消費しない。確認画面のPOSTで`verifyOtp`を実行し、Cookieを設定する。メール確認は`email`、再設定は`recovery`だけを受け付ける。遷移先はワークスペース・再設定・招待の既知のアプリ内パスに限定する。
- 再設定メールの受付はアカウントの有無を明かさない。同じブラウザでなくてもメール確認を完了できる。新パスワードは確認入力と照合し、認証された本人だけが保存できる。
- フォームはOrigin・Content-Type・4KiB上限・重複フィールド・入力値を検査する。パスワード、トークン、メール本文をログへ記録しない。Supabase Authの制限を維持し、429時は待機を案内する。
- 新規ユーザーの既定表示名は「新しいメンバー」。登録時の有効な表示名を使用するが、メタデータからロール・所属・権限を設定しない。
- 認証済み本人は所属の有無によらずワークスペースを作成でき、作成者だけをadminにする。名前は前後空白除去後1〜120文字。作成は24時間の再送制御を持ち、同じキー・本文は同じ応答、本文違いは409。通常ユーザーの直接書込は禁止する。
- ワークスペース再送記録にも既存の期限切れ定期削除を適用する。既存5種類の削除方式と有効記録・操作履歴の保持を維持する。

## 検証

ローカルSMTPに配送した確認・再設定メールから実際のリンクを取得し、確認前拒否・GET未消費・POST確認・同一トークン再使用拒否・別ブラウザでの確認・再設定後の認証を確認する。外部宛てにテストメールを送信しない。Origin、入力上限、Preview停止、作成再送・競合・所属分離をDB/認証E2Eで確認する。

本番の有効化状態と実施した範囲は運用手順に記録する。メール送信サービスの設定が未完了の状態を「本番利用可能」と扱わない。
