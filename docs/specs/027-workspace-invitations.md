# メールによるワークスペース招待

Issue #79。管理者がメールアドレスを指定して招待し、メールの所有者が確認・承諾した後で所属を追加する。管理者ロールの招待、一般利用者からの招待、任意のメール本文、送達/開封追跡は対象外。

## 招待と権限

- 管理者だけが同じワークスペースへのmember/viewer招待を作成・一覧・取消・再送できる。メールは前後空白除去と小文字化を行い、最大254文字とする。
- 有効期限は作成・再送から7日。トークンは暗号学的乱数32バイトのbase64url（43文字）とし、DBにはSHA-256 digestだけ保存する。トークン、確認メール本文、宛先メールを操作履歴へ保存しない。管理者の管理一覧には宛先メールを表示する。
- 同じ宛先への有効な未承諾招待はワークスペースごとに1件とする。取消・再送はversionによる競合を検出する。再送ではトークンを回転し、旧リンクを無効にする。
- 承諾はログイン済み本人の現在のauth.users.emailとemail_confirmed_atをDBで照合する。未認証・別メールにはワークスペース名などを返さない。JWTの自己申告メールや未確認メールだけでは所属を付与しない。
- 承諾時も招待元の現在の管理者権限、招待状態・期限を再検査する。所属は承諾と同一トランザクションで作成する。既存所属は変更せず、既存管理者を降格しない。承諾済みの再実行では所属を再作成しない。

## 送信と再送

Supabase Authの`signInWithOtp`と設定済みSMTPを使い、アプリに管理鍵を追加しない。新規ユーザーを許可し、確認メールのリンクは`/confirm?next=/invitations/:token`とtoken_hash/type=emailを使う。メール内リンクを開くだけでは確認・承諾を実行しない。確認ボタンでPOSTして認証を完了し、招待画面の承諾ボタンでもう一度POSTする。

`SELF_SERVICE_AUTH_ENABLED=true`の環境だけで送信・メール確認・承諾を提供する。本番SMTPの送信元ドメイン、認証設定、テンプレート、環境変数が未設定の場合は無効のままとし、本番反映完了と扱わない。ローカルはSMTP受信箱とexample.invalidを使い、外部へメールを送らない。

作成・再送・取消はIdempotency-Keyで24時間の再試行に対応する。同じキーの同じ操作はDB受付を再利用し、メールは再送しない。生トークンを保存しないため、通信結果不明時は管理一覧で状態を確認し、明示的な「再送」で新しいトークンへ回転する。

送信状態は`pending`（送信状況未確定）、`sent`（認証サービスが送信を受付）、`failed`（送信失敗）を区別する。sentは到着・開封・承諾の保証ではない。DB受付後の送信失敗は招待を保留して再送できる状態にする。送信受付の応答が失われても、実際に届いた有効なリンクと確認済みメールの所有者は承諾できる。送信状態だけでは所属を付与しない。

## APIと画面

- `GET/POST /api/v1/workspaces/:wid/invitations`：管理一覧（既定25・最大100件、created_at/id keyset）と作成`{email,role}`。作成時Idempotency-Key必須。
- `POST /api/v1/workspaces/:wid/invitations/:id/resend`・`/cancel`：`{version}`とIdempotency-Key必須。
- `POST /api/v1/invitations/:token/accept`：JSON空オブジェクト。本人確認後の承諾のみ。トークンを応答に含めない。
- `/members`に管理者用の招待フォーム・状態一覧・再送/取消を追加する。送信状態と承諾状態を分け、再送で旧リンクが使えなくなることを案内する。
- `/invitations/:token`は`Referrer-Policy: strict-origin`（送信元のパス・クエリを送らない）とし、未認証では一般的なログイン/登録案内だけを表示する。確認済みの招待先本人にはワークスペース名・ロール・期限と承諾ボタンを表示する。別メール、期限切れ、取消済み、無効なトークンは同じ利用不可表示とする。
- ログイン・登録は許可した`next=/invitations/:token`だけを引き継ぐ。外部URLやその他の任意パスへ遷移させない。
- APIは認証401、管理者以外403または所属外404、不正入力400、競合409、Origin403、形式415、32KiB超413、private/no-storeとする。エラーに内部SQLやトークンを含めない。

## DBと保持

migration020でprivate.workspace_invitationsとprivate.invitation_requestsを追加し、直接アクセスを拒否する。SECURITY DEFINER・空search_path・project_hub_owner所有のRPCが現在の操作者から権限を確定する。authスキーマ・auth.usersの権限やRLSを変更しない。現在の確認済みメールの取得だけは、引数なし・空search_path・STABLE SECURITY DEFINERのprivate.invitation_verified_email()へ限定する。同関数は管理環境のpostgres所有（BYPASSRLS）とし、固定SQLでauth.uid()本人のemail/email_confirmed_atだけを検査する。呼出権限はproject_hub_ownerだけへ付与し、PUBLIC・anon・authenticated・service_roleから取り消す。これはAuth所有テーブルを変更できないホスト環境に対応する限定的な例外であり、ユーザーIDを指定した参照やアプリへの管理鍵追加は行わない。

招待の作成・状態/version変更は、既存の監査関数でrole/status/versionだけを記録する。メール送信の結果更新と古い招待の保守削除は操作履歴へ追加しない。所属作成の履歴は既存のmemberships監査を維持する。

再送記録は24時間、招待管理レコードは期限終了後30日まで保持する。管理者用bounded purgeと毎時のpg_cronで各表最大1,000件、通常利用者とservice_roleの実行は禁止する。同ジョブの完了後7日超の実行履歴を最大10,000件ずつ整理する。pg_cronが使えない環境では関数だけ導入し、本番の実行確認と区別する。削除後も既存の所属・操作履歴は残す。

## 検証

DBで管理者境界・現在のメール確認・期限/取消/回転/再送/競合・同時承諾・既存所属維持・受付キー再利用・所属解除後の再承諾禁止・監査の本文非記録を確認する。認証E2EはローカルSMTPの実際のリンクを別ブラウザで確認し、明示承諾まで所属がないこと、別メールの拒否、PC/360px、送信失敗・再送と旧リンク無効を確認する。実行・本番SMTPの有効化は統合側で行う。
